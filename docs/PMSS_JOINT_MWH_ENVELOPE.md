# 第十二阶段：24小时联合机组约束下的候选报价电量范围

## 核心目标

以前对新报价的“最小—普通LP—最大”中标量区间来自24个互不相干的逐小时DC线性规划，不能保证跨小时的机组爬坡、启停和最短连续开停机时间成立。

本次新模块先在同一个24小时联合DC+UC混合整数规划中，求原始申报报价成本与启停成本之和的最低值C*，再添加总经济成本不超过C*加公开的小容差。随后分别以目标机组全天累计中标MWh最小、最大为次级目标，重新求解完整24小时网络和机组物理约束。

这样得到**两套独立的24小时完整可行调度**：全天MWh最少的一套、最多的一套。两套方案可能采用不同机组开停状态，其逐时出力轨迹可交叉，不是逐小时上下界。

## 代码

- src/powerbid/joint_market.py：增加可选的24小时目标机组中标MWh极值求解模式。沿用原网络节点平衡、线路DC潮流、报价成本、机组开关机、启停爬坡、连续运行爬坡和最短开停机约束；原普通市场求解默认行为保持不变。二级MILP只输出全天MWh、24小时发电与在线状态、原最佳成本和成本差，不输出误导性节点LMP或结算价。
- src/powerbid/joint_candidate_bounds.py：增加完整源证明准入和两次全日极值求解，严格核对全部机组技术参数。
- app/pmss_api.py：新只读接口 POST /api/pmss/network-joint-mwh-range，沿用当前凭据过滤、请求大小、有限并发和报价合法性约束。
- frontend/src/PMSSJointMwhPanel.tsx：在已有候选报价区间面板下增加“课程核实技术JSON”手动上传、来源说明、用户确认及联立24小时两条物理可行调度轨迹。

## 真实PMSS资料准入限制

平台已有原始只读技术字段并不足以确认其实际含义、单位及设备边界，也不包含完整可靠的初始开停机、初始功率、持续状态和启停过渡参数。**不会根据历史中标量、机组容量或字段名称猜测填充缺项**。

- 必须逐机组提供严格完整的ThermalConstraints参数，ID完整一致，不能缺字段或引入认证信息。
- 人工核实课程来源需要明确由用户声明为course_verified_by_user，并提供具体课程说明；但该标签**不等于PowerBid已经独立核实老师PMSS实际使用了这些参数**。
- API的synthetic来源只允许用于明确的人工合成教学测试，不可当作真实市场物理依据；来源不明和user_supplied_unverified会被拒绝。
- 缺机组、参数错误、非法新报价、成本边界不可证、模型不可行或超时均拒绝伪造结果。
- 研究上限12台机组、60个节点、90条线路；依旧不向老师PMSS保存报价或执行出清。

## 明确限制

新结果是在同一批历史同行报价与脱敏网架输入下的**简化 DC+UC 经济最优日发电区间**，不是未来PMSS的真实电量预测区间。未知的AC损耗、系统备用、N-1、老师特殊结算价格以及多日期鲁棒性都未被核实。

之前单日1001节点电价上限只是事后数值拟合假设，本次不将它写入正式结算或利润计算；没有生成虚假的收益区间。

运行全项目pytest、ruff、Python编译及GitHub Node22/TypeScript npm run build。合成测试验证两个不同最优日电量方案、机组初始状态/爬坡导致的日范围收窄，以及缺参数、非法价格、来源不可信和未知字段必须拒绝。
