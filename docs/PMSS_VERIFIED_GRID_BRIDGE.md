# 真实 PMSS 39 节点网架 → PowerBid 现有 DC 报价策略引擎

本阶段重点是把**服务器已获授权、只读获取的真实节点/线路/机组参数**接到主分支已有的 `network_dispatch.py` 和 `network_strategy.py`，而不是另外重写电力市场。

## 已验证的 2025-09-01 日前案例

- 39 个 Bus、46 条支路、10 台机组、24 时段节点负荷；
- 网架线路电抗均为正，约 0.0026—0.0625；额定容量 405—1115 MW；
- 机组接入节点均有对应，所有支路两端节点有效，电网连通；
- PMSS 已出清结果的机组、节点、支路 `elementId` 分别与网架中的机组、节点、线路原始 ID 完整匹配（10/39/46）。
- 全部线路的变比字段 `ratio=1`。非 1 时导出器会拒绝，不能偷偷按普通线路处理。

已用真实网架做24小时 DC 有功潮流/线路上限约束求解，各小时都有可行解。在该案例下，原提交报价的本地 DC 线性模型与 PMSS 历史记录相比：46条线路×24时段的**绝对潮流 MAE 约43.34 MW**，39节点×24时段的**电价 MAE 约397.37**（未经完整结算口径核对，价格差距较大）。不同机组中标量误差显著不同，不能只挑选误差接近0的机组宣布模型准确。

这不代表 PMSS 的 AC/机组组合/备用/真实价格规则已复制，更不代表新报价经过 PMSS 重出清。

## 严格数据源边界

只在可信服务器、具备读取权限的上下文中执行：

```sh
python scripts/merge_pmss_grid.py \
  --snapshot /tmp/powerbid_pmss_readonly_2025-09-01.json \
  --grid /srv/powerbid-platform/pmss-grid-snapshot.json \
  --output /tmp/powerbid_pmss_dc_verified_2025-09-01.json
```

- 新的脱敏快照增加 `dcNetwork` 字段，其结构**直接兼容现有** `network_from_dict`。
- 输出采用原 PMSS 网络 ID 来关联历史结果，但是不含登录凭证、Cookie、Token、工程会话和其他未经允许的原始字段。
- 输出文件保存在 Git 工作区外、0600 权限；拒绝覆盖已存在文件或源文件。
- 不修改原有 PMSS 场景，不调用报价保存和市场出清。
- 39节点网络源文件仅存储于受控服务器，不提交 GitHub。

原始源文件未提供明确 `baseMva`。在变比全部为1、单一公共电抗基准的无损 DC 模型中，统一缩放相角不改变潮流和节点边际价格，因此导出时将 `baseMva=1.0` **只作为计算归一化尺度**。它不是来自 PMSS 的真实电压相角或基准容量，不应宣称两者已核验。

## 网页使用方式

在 React Studio → **PMSS 市场分析**：

1. 载入由受信服务器生成的脱敏 JSON。没有 `dcNetwork` 时旧页面及五段报价仍可以使用，但不允许网络重算。
2. 运行原来的五段量价候选搜索，得到单区域教学模拟建议。
3. 点击 **运行真实拓扑网络对照**，后端用既有 DC 引擎对历史原报价和当前候选分别逐小时复算，展示目标机组中标 MW、模拟边际价、线路容量约束活跃的小时数。
4. 同屏对照 PMSS 历史真实中标，但**不会**把历史结果误认为新报价的 PMSS 反馈，也不会假装当前推荐的利润得到老师平台验证。

后端调用 `evaluate_network_plan`，始终只用一个中性场景；单独的 `network_strategy.compare_network_policies` 已具备风险情景策略比较，避免开发两套重复算法。HTTP 入口限流、限制请求尺寸/节点数/机组数，计算过程仅在本地内存中进行。

当前仍未把机组启停、爬坡、备用和最小技术出力作为联合 DC 优化约束；已有的机组约束 MILP 是独立模块，不能将其与上述逐小时 DC LP 混为一谈。
